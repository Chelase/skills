# 项目专用技能目录（skills/）

本目录存放本项目在开发过程中沉淀的专用技能：可复用的操作流程、检查清单、脚本与产出模板。

## 判据

写"这件事具体怎么做"的可复用操作流程（步骤 + 可选脚本/模板），放本目录。
若只是"必须 / 不要 / 优先"的执行约束，放 `../rules/`；若是系统现状与链路事实，放 `../mechanisms/`；若是本期实施计划，放 `../dev-plans/`；若是外部规范与学习笔记，放 `../docs/`。

## 与 rules/ 的分工（成对使用）

| | `rules/` | `skills/` |
|---|---|---|
| 回答什么 | 什么时候用、允不允许用、用之前要过哪些检查 | 具体怎么做 |
| 权威性 | 硬约束，优先级高于技能 | 操作手册，不得突破规则 |
| 谁引用谁 | 规则里写「配套技能」表 | 技能里反向写「配套规则」 |

三条硬约定：

1. 规则决定是否调用技能；技能不得自行扩大权限、跳过规则中的校验步骤或改变规则优先级。
2. 技能新增后必须至少被一条 `rules/` 规则引用（规则文件内写「配套技能」段）。没有引用的技能不会被自动触发，属于孤儿技能，需补登记或删除。
3. 规则侧「配套技能」表与技能侧「配套规则」必须一致；改任何一边，同步改另一边。

## 沉淀门槛

同一套流程在本项目重复执行 **≥ 3 次**、形态稳定、且包含项目特有信息，就必须固化为技能（高风险不可重试的流程可提前沉淀并注明理由）。
完整判据、五步流程、验收门槛与废弃规则见 `../rules/skill-capture.md`，不要凭感觉新建技能。

## 技能单元结构

一个技能一个目录：

```
skills/<name>/
├─ SKILL.md        # 必需：技能说明与执行步骤
├─ scripts/        # 可选：可直接执行的脚本
├─ templates/      # 可选：产出模板
└─ references/     # 可选：长参考资料，按需读取，不默认载入
```

`<name>` 用语义化短横线命名，且必须与 `SKILL.md` frontmatter 的 `name` 完全一致。

## SKILL.md 约定

frontmatter 必填两项：

```yaml
---
name: <与目录同名>
description: "一句话说明做什么、何时用、何时不要用；带上触发词，便于 Agent 判断是否加载"
---
```

正文推荐结构（标题可微调，语义不能变）：

1. **适用场景**：命中什么任务才用。
2. **前置检查**：用之前必须先读哪些规则、机制文档。
3. **执行步骤**：编号步骤，可验证、可复现。
4. **产出**：写到哪、什么格式。
5. **边界与禁止**：什么时候不要用、不许做什么。
6. **验证方式**：怎么判断这次做对了。
7. **配套规则**：反向指回触发它的规则文件与章节。

技能正文保持简短，长参考资料放 `references/`，只在执行到那一步时读取；不要把整套规则或机制正文复制进来。

## 规则侧标注格式

在触发该技能的规则文件末尾增加一段：

```markdown
## 配套技能

| 技能 | 何时使用 | 何时不要用 | 怎么用 | 关联章节 |
|---|---|---|---|---|
| `skills/<name>/SKILL.md` | 触发条件 | 明确排除的场景 | 先读「前置检查」再按「执行步骤」 | §x |
```

表格固定五列。没有这张表的技能不会被 Agent 主动加载。

## 不放进本目录的内容

- 纯执行约束（必须 / 不要 / 优先）→ `../rules/`
- 系统现状、接口契约、链路事实 → `../mechanisms/`
- 本期实施计划与验收步骤 → `../dev-plans/`
- 外部规范摘要、学习笔记 → `../docs/`
- 一次性脚本、临时命令 → 放项目自己的脚本目录，不进技能库
- 通用能力（跨项目都能用）→ 放全局技能目录，不复制进本项目

## 规模与索引

- 本 README 是本目录的一层索引，不是技能正文的堆放处。
- 技能数量明显变多（例如超过 12 个）时，按业务域或能力主题拆分子目录，每个子目录保留自己的 `README.md` 索引。
- Agent 先读本索引定位技能，再精读目标 `SKILL.md`；不要逐个目录盲找，也不要一次性全部载入。
